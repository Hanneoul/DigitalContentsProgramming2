최종 평가: Dungeon Escape NPC AI 만들기
======================================

1. 목표와 제출 범위
배정된 playerN.c의 playerN_choose_command(const char *state_path) 함수 하나만 수정한다.
N은 조 번호 0~5이다. 반환형은 Command이며 player_api.h에 정의된 상하좌우 중
하나를 반환한다. 코어, 헤더, 맵, 다른 조의 코드와 파일을 수정하거나 참조하면 안 된다.
제공된 예제는 너비 우선 탐색(BFS)으로 열쇠와 출구까지 최단 경로를 찾는다.
평가에서는 강사가 다른 맵을 사용할 수 있다. 특정 맵 좌표를 하드코딩하지 말 것.

2. 게임 규칙
- 6개 조가 참가하며 P0~P5가 각 시작 위치이다. 행과 열 좌표는 0부터 시작한다.
- 한 라운드에 각 플레이어가 한 번씩 행동한다. 첫 라운드는 P0부터,
  두 번째는 P1부터 시작하며 매 라운드 선두가 순환한다.
- 한 행동은 상하좌우 한 칸이다. 벽이나 필드 밖이면 제자리에 머무른다.
- 같은 칸에 여러 플레이어가 설 수 있다. 충돌, 공격, 열쇠 빼앗기는 없다.
- 열쇠 칸에 먼저 도착한 플레이어가 유일한 열쇠를 획득한다.
- 열쇠 소유자가 출구 칸으로 이동하는 즉시 승리한다.
  열쇠가 없는 플레이어도 출구를 통과할 수 있지만 문은 열리지 않는다.
- 기본 최대 200라운드이며 승자가 없으면 무승부다.
- 각 행동 전 기본 2초를 기다려 직전 화면을 확인할 시간을 준다.
- 명령은 COMMAND_UP=0, COMMAND_DOWN=1, COMMAND_LEFT=2, COMMAND_RIGHT=3이다.
  별도 대기 명령은 없다. 범위 밖 반환값, 비정상 종료, 1.5초 실행 제한 초과는
  해당 행동을 무효 처리하고 playerN_diagnostics.log에 기록한다.
- UI의 +N은 여러 플레이어가 겹친 칸이다. 열쇠 소유자를 우선 표시하고,
  모든 플레이어의 실제 위치는 아래 상태 줄에 표시한다.

3. dungeonmap.dat 작성법
ASCII 텍스트, BOM 없이 저장한다. LF/CRLF 모두 가능하다.
3~32 크기의 n*n 정사각형이며 한 줄은 정확히 2*n 글자여야 한다.
공백과 행 끝 공백도 데이터이므로 지우지 말 것. 탭은 사용할 수 없다.
  ## : 벽 (회색 글자와 배경)
  두 칸 공백 : 바닥 (배경 없음)
  P0 ~ P5 : 각 조 시작점, 각각 정확히 한 개
  P6 ~ P9 : 시작점으로 등록하지 않고 바닥으로 처리
  @- : 노란색 열쇠, 정확히 한 개
  () : 출구, 정확히 한 개
모든 시작점과 출구는 열쇠에서 벽을 통과하지 않고 도달 가능해야 한다.
플레이어가 이동하면 시작점은 바닥이 된다. 열쇠를 획득해도 출구 지형은 유지된다.

4. 매 행동 직전 제공되는 상태 파일
함수 인자로 전달된 state_path만 읽기 모드로 열어 사용한다.
각 호출 직전 코어가 최신 상태를 저장하고 파일을 닫은 후 AI 프로세스를 실행한다.
즉 같은 라운드에서 앞서 행동한 플레이어의 이동도 반영된다.
실행마다 별도 run-프로세스ID-시각 폴더를 만들고 조별 최신 상태 파일을 덮어쓴다.
상태 파일은 다음 형식이다.

FGC_STATE 1
n round turn self key_owner key_row key_col exit_row exit_col
0 p0_row p0_col
1 p1_row p1_col
2 p2_row p2_col
3 p3_row p3_col
4 p4_row p4_col
5 p5_row p5_col
이어서 정확히 n줄의 지도 (한 칸 2글자)

round는 1부터 시작하는 라운드, turn은 1부터 시작하는 전체 행동 번호이다.
self는 이번에 명령을 반환할 조 번호, key_owner는 미획득 시 -1, 획득 후 조 번호다.
key_row/key_col은 획득 이후에도 원래 열쇠 위치이다. key_owner를 반드시 확인한다.
지도 부분에는 P0 등의 문자열이 없으며 플레이어 위치는 위의 숫자 6줄로 확인한다.
지도에는 ##, 공백, (), 그리고 아직 획득하지 않은 @-만 들어 있다.
공백을 보존하려면 지도 행은 fgets로 읽는다. fscanf 뒤의 개행 처리에 유의한다.
학생용 예제는 각 .c에서 직접 fopen/fscanf/fgets/fclose를 사용한다.

5. 메모리와 파일 자원 관리 (평가 대상)
malloc/calloc/realloc 성공 여부를 확인하고 반환 전에 반드시 free한다.
fopen/fopen_s 성공 여부를 확인하고 반환 경로마다 fclose한다.
player_api.h를 포함하면 위 함수 호출은 추적 매크로를 통과한다.
Debug 빌드에서는 MS CRT의 _malloc_dbg 계열로 할당 파일/줄 번호를 기록하고,
AI 함수 반환 후 _CrtCheckMemory, _CrtDumpMemoryLeaks를 실행한다.
fopen/fopen_s는 별도 추적기로 관리하므로 fclose 누락도 파일/줄 번호가 나온다.
FILE 누수는 보고 후 닫아 주지만 이는 학생의 정상적인 자원 정리를 대신하지 않는다.
같은 포인터를 두 번 fclose하거나 추적하지 않은 FILE을 fclose하면 오류로 기록한다.
조별 진단 로그와 Visual Studio 디버그 출력을 확인할 것. 정상 로그는 비어 있다.
메모리 누수 검사는 Debug에서만 제공하며 파일 추적은 Release에서도 동작한다.
매크로를 우회하거나 freopen, _open, Win32 핸들 등의 별도 API를 쓰면 파일 추적
대상이 아니다. 학생 코드는 제공된 fopen/fopen_s/fclose만 사용할 것.
타임아웃, exit/abort, 강제 종료 시 반환 후 검사를 실행할 수 없으므로 코어가
비정상 실행을 기록한다. 모든 종류의 오류에서 정확한 소스 줄을 보장하지는 않는다.

6. 실행과 검증 (강사용)
Visual Studio에서 FinalExamGameCore를 시작 프로젝트로 지정한 뒤 빌드/실행한다.
모든 소스는 .c이며 /TC 및 C17 모드로 빌드한다. main 함수는 main.c에 있다.
Debug/Release, x64/Win32 구성을 지원한다.
실행 파일은 프로젝트 내부 bin\플랫폼\구성에 생성되고 맵도 자동 복사된다.
기본 맵은 실행 파일 옆에서 읽으므로 실행 시 작업 폴더가 달라도 동작한다.
  FinalExamGameCore.exe
  FinalExamGameCore.exe --fast --plain
  FinalExamGameCore.exe --map "다른맵.dat" --max-rounds 100
  FinalExamGameCore.exe --self-test
--fast는 화면 사이 2초 대기를 생략한다. --plain은 ANSI 색/화면 지우기를 끈다.
출력을 파일로 리디렉션하면 자동으로 ANSI 코드를 사용하지 않는다.
--map의 상대 경로는 현재 작업 폴더 기준이다. 맵 변경 후 다시 빌드하면 복사된다.
verify.ps1은 네 가지 구성 빌드, 규칙/맵/스냅샷/AI 테스트와 완주를 검증한다.
또한 verification 폴더의 별도 복사본에서만 의도적인 누수, 이중 fclose,
시간 초과, 크래시, 무효 명령을 주입해 로그와 코어의 계속 실행을 검증한다.
최종 화면의 Snapshots / diagnostics 경로에서 상태와 조별 로그를 확인한다.

7. 소스 보호와 운영상 제한 (강사용)
학생에게는 자기 playerN.c, player_api.h, diagnostics.h, 이 문제와 연습용 상태
파일만 별도 폴더로 배포한다. 모든 소스가 든 강사용 저장소를 학생과 공유하지 않는다.
제출된 playerN.c는 강사가 검토한 후 이 프로젝트에서 통합 빌드한다.
다른 조의 함수 선언과 디스패처는 runner.c에만 있다. 코어의 Game 포인터는
학생 함수에 전달되지 않으며 AI는 매 행동 별도 프로세스에서 실행된다.
따라서 전역/static 변수는 다음 행동까지 유지되지 않는다. 다른 파일에 상태를
저장하지 말고 제공된 상태 파일을 이용해 매번 판단한다.
프로세스 분리는 코어 메모리 보호와 무한 루프 제한을 위한 것이며 보안 샌드박스는
아니다. 같은 Windows 계정 권한으로 파일을 열거나 API를 호출하는 행위를 막지는
못한다. 악의적인 제출물은 실행하지 말고, 강한 격리가 필요하면 조별 별도 OS 계정
및 파일 ACL 또는 VM을 사용한다. C 소스 파일 분리만으로 열람 차단은 불가능하다.
경로 처리는 Windows ANSI API 기반이므로 현재 시스템 코드 페이지에서 표현할 수
있는 경로를 사용하고, 긴 경로는 피한다.
